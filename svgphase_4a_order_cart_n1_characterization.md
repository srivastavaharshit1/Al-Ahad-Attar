# Phase 4A Order/Cart N+1 Characterization

## 1. Scope
Analyze the `OrderServiceImpl.createOrder` and `CartServiceImpl` (`evaluateGuestCart`) methods to trace exact database query patterns generated by `for` loops during order processing and cart sync. Characterize behavior, exceptions, transaction safety, and test coverage to determine if N+1 optimizations using `findAllById` are completely safe.

## 2. Order Creation Query Pattern
The `createOrder` method contains FOUR sequential iterations over the order items:
- **First pass (paid items):** Loops over `request.getItems()`. Fetches `ProductVariant` via `variantRepository.findById()`. Fetches `Bottle` via `bottleRepository.findById()` if applicable.
- **Second pass (free items):** Loops over `request.getItems()`. Fetches `ProductVariant` via `variantRepository.findById()`.
- **Third pass (stock validation):** Loops over `cartEval.getItems()`. Fetches `ProductVariant` via `variantRepository.findById()`.
- **Fourth pass (order generation):** Loops over `cartEval.getItems()`. Fetches `ProductVariant` via `variantRepository.findById()`.

## 3. Cart Query Pattern
- **CartServiceImpl.evaluateGuestCart:** Iterates over `request.getItems()`. Fetches `ProductVariant` and `Bottle` individually inside the loop for every cart item.

## 5. Current Logical Query Counts
For an order with `N` paid items (Attars with bottles) and `M` free items:
- **1 item (1 paid + bottle, 0 free):** 4 variant queries + 1 bottle query = 5 queries.
- **3 items (3 paid + bottle, 0 free):** 12 variant queries + 3 bottle queries = 15 queries.
- **5 items (5 paid + bottle, 0 free):** 20 variant queries + 5 bottle queries = 25 queries.
- **10 items (8 paid + bottle, 2 free):** 38 variant queries (32 for paid + 6 for free) + 8 bottle queries = 46 queries.

## 6. Behavioral Dependencies
- **Ordering:** The checkout loop evaluates cart items sequentially. Replacing sequential DB lookups with an in-memory `Map` lookup strictly preserves the sequential evaluation order.
- **Lazy Relationships:** `ProductVariant.product` is accessed (`variant.getProduct().getName()`). The `Product` proxy is loaded safely via an existing `@BatchSize(size = 20)` annotation, meaning batched variant fetching will not inadvertently trigger a lazy-loading N+1.

## 7. Exception Behavior
- **Current:** If `variantId=99` is missing, `findById().orElseThrow()` halts execution at the exact loop iteration index where `99` occurs, throwing `ResourceNotFoundException("Variant not found: 99")`.
- **Proposed Batching:** Using `findAllById(allIds)`, missing IDs won't be returned. The loop will execute `variantMap.get(99)`, return null, and manually throw `ResourceNotFoundException("Variant not found: 99")`. **Exception behavior is 100% preserved.**

## 8. Duplicate-ID Behavior
- **Current:** If the cart contains two separate requests with `variantId=5`, `findById(5)` is called twice (Hibernate L1 cache optimizes the second call, but semantics are identical).
- **Proposed Batching:** `findAllById(Set.of(5))` executes once. The loop will look up `variantMap.get(5)` twice. **Duplicate behavior is 100% preserved.**

## 9. Transaction/Stock Safety
- The most critical behavior is stock locking. `variantRepository.decrementStock(variant.getId(), quantity)` performs an atomic SQL `UPDATE`. 
- Pre-fetching entities into a Map before the loops does not alter transaction boundaries, lock states, or isolation levels. It merely replaces `SELECT` loops with a batched `SELECT IN (...)`.

## 10. Existing Test Coverage
- `OrderConcurrencyIntegrationTest.java`: Protects atomic stock reduction and webhook transaction boundaries under concurrent load.
- `OrderServiceIntegrationTest.java`: Checks standard success paths.

## 11. Missing Characterization Tests
- `OrderServiceImpl`: No explicit test asserting failure when a *specific* item index in a multi-item cart is missing (to prove the exact fail-fast sequence is retained).
- `CartServiceImpl`: No dedicated tests for `evaluateGuestCart` asserting missing variant IDs.

## 12. Proposed Batching Strategy
1. Iterate over `request.getItems()` to collect `Set<Long> variantIds` and `Set<Long> bottleIds`.
2. Execute `variantRepository.findAllById(variantIds)` and `bottleRepository.findAllById(bottleIds)`.
3. Construct `Map<Long, ProductVariant>` and `Map<Long, Bottle>`.
4. Keep the exact original loops (4 passes), but replace `variantRepository.findById(id)` with `Optional.ofNullable(variantMap.get(id))`.
5. Retain all `.orElseThrow(...)` behavior exactly where it is.

## 13. Benchmark Strategy
- No dedicated SQL logging is currently active (e.g., `hibernate.generate_statistics`).
- **Temporary Benchmark:** Enable `spring.jpa.properties.hibernate.generate_statistics=true` locally during implementation to visually confirm the drop in `JDBC statements executed` from ~46 to ~2 during a 10-item checkout test.

## 14. Risk Classification
- **OrderServiceImpl.createOrder:** Class A (Safe to batch directly). 
- **CartServiceImpl.evaluateGuestCart:** Class A (Safe to batch directly).
Because the mapping pattern perfectly preserves iteration order and null-handling semantics, no characterization tests are strictly required before proceeding.
